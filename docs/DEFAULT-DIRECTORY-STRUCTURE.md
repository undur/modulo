## Notes, thoughts and ideas

* The stack's default directory name `/opt/wo` - suggestion, not decided
* The stack's default user name `wo` - suggestion, not decided
* Might want to include an `{app}/conf/` directory for app-specific properties
* Same for app-specific _modulo_ config (although app-level proxy configuration should really only be performed by and obtained from wotaskd. That might change, though)
* Possibly use folders for all log files. Multiple rotated log files generate a lot of noise
* Archive folders for backup copies of apps (bundles archived when a new app is deployed). Applies to both deployed apps and the stack apps.
* Alternative considered, parked: give the stack's own apps the *same per-app structure* as deployed apps — a folder per stack app holding its bundle and log files, exactly like an `apps/` entry. Deepens the hierarchy on disk, but it's a mental simplification: one structure to know, wherever an app lives.
* `acme/sites/` → `acme/certs/` — decided. Doubly misnamed: it collides with the top-level `sites/`, and it names the map's key (hostnames) rather than its contents (certificates). Rename happens with the big layout migration: one path constant in modulo's AcmeSettings, a `mv` per server, and a startup fallback that adopts an existing `sites/` so renewal state can't be stranded.
* The name of `sites/` — open question. The doubt: it's a folder containing only configuration files, and you can't deduce that from the name; "sites" suggests the sites themselves live there. The counter-argument: in this design they *do* — a site owns no files, it *is* its routing entry, so the config file is the site, and `ls sites/` honestly answers "what does this server serve" (mirroring `apps/` = "what's deployed"). Candidates weighed: `siteconfig` is unavailable (already taken by wotaskd's unrelated `SiteConfig.xml` store — a twin name would be cruel); `modulo.d` is accurate in the conf.d tradition but names the consumer, not the content; `sites.d` is the best rename if the fragment-ness should be signaled, at the cost of breaking the layout's voice (no other directory is named for its mechanism). Staying `sites/` for now; both instincts recorded.


## Suggested default directory layout
First draft for the default server layout, used by the server setup script

```
/opt/
  ├── jdk-26/                                JDK
  │
  └── wo/                                    the stack — owned by the `wo` user
      │
      ├── modulo.toml                        modulo's basic config
      │
      ├── stackapps/                         the stack's own apps — "stack" in the name to keep their role distinct from apps/
      │   ├── wotaskd.woa                    
      │   ├── JavaMonitor.woa                
      │   ├── modulo.woa              
      │   └── x-modulo.woa-prev-…/    previous builds, moved aside by upgrades
      │   
      ├── siteconfig/                        wotaskd's config store
      │   ├── SiteConfig.xml                 
      │   └── SiteConfigBackup.xml.<timestamp>.<action>.gz
      │
      ├── stacklogs/                         the stack's logging, one log per service
      │   ├── modulo.log                     
      │   ├── wotaskd.log
      │   ├── javamonitor.log                
      │   └── access/                        per-site access logs — written, rotated and pruned by the front end
      │       ├── www.example.com/           a directory per site, a file per day
      │       │   ├── 2026_08_31.log
      │       │   └── 2026_09_01.log
      │       ├── shop.example.com/
      │       │   └── …
      │       └── …
      │       
      ├── acme/                              certificates — deliberately global: one certificate can cover several sites
      │   ├── account-key.pem                keypair identifying the ACME account at the certificate authority. Generated by modulo on first request to the authority
      │   └── certs/                         one directory per canonical hostname ("certs", not "sites" — it holds certificates, and the top-level sites/ already owns that word)
      │       ├── www.example.com/           
      │       │   ├── cert.pem
      │       │   └── key.pem
      │       ├── shop.example.com/
      │       │   └── …
      │       └── …
      │       
      ├── apps/                              one directory per application — keyed by app name, holds only app-owned files
      │   ├── Website/
      │   │   ├── app/
      │   │   │   ├── Website.woa            the deployed bundle
      │   │   │   └── x-Website.woa-prev-…/  previous builds
      │   │   └── log/                       instance logs
      │   │       ├── Website-1.log          
      │   │       └── Website-2.log          
      │   ├── Shop/
      │   │   ├── app/   Shop.woa
      │   │   └── log/   ...
      │   └── Blog/
      │       ├── app/   Blog.woa
      │       └── log/   ...
      │       
      └── sites/                             site-specific modulo configuration files (host default apps, hostname aliases, canonical hostname, URL rewrites etc.).
          │                                  Filenames are convention only — naming a file after its canonical hostname keeps `ls sites/` meaningful, but identity
          │                                  comes from each [[sites]] entry's hostnames array (first = canonical), and one file may hold several [[sites]].
          ├── www.example.com.toml           → Website, with /blog/* routed to Blog     (one site, several apps)
          ├── shop.example.com.toml          → Shop
          ├── shop.example.org.toml          → Shop                                     (one app, several sites)
          └── www.example.net.toml           → Blog
```
